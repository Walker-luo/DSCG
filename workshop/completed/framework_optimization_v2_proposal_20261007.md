# DSCG 下一轮框架优化方案

日期：2026-10-07。状态：**架构提案，尚未实施**。依据：[最新结果复核](framework_optimization_review_20261007.md)、[用户的精简约束](framework_optimization_direction_20261007.md)。本方案给出框架职责、优化顺序和验收，不解锁论文机制或宣布防御收益。

## 1. 主线与备选

**先用两个阶段修好两层，再用一个阶段决定是否转三层。每层只负责一个问题。** 暂不追加默认重审、自动恢复、第二个动作审计器或多 Agent。

| 路线 | 作用 | 取舍 |
|---|---|---|
| A：精简并修正两层（推荐先做） | 工具授权负责“能用什么”，动作审计负责“这次调用是否属于任务” | 直接对应当前漏授权、缺上下文的已知失败；改动集中 |
| B：三层候选 | 在任务授权、动作审计之间加入工具返回处理层 | 仅在 A 仍存在外部指令影响、且有效对照没有安全净收益时启动；要支付额外处理成本并验证内容保留 |
| C：仅确定性 P0 对照 | 保留授权、Monitor、ticket，关闭语义审计 | 使用现有 --no-checker 分离两层各自的代价与收益，作为实验对照 |

当前工具级 P0 的 Monitor/ticket 是执行基础设施，不因内部模块多就计算成更多防御层。架构图中的“工具授权”不是对象/参数/数据权限保证。

## 2. 阶段一：让工具授权简单且稳定

```text
可信用户任务 + 宿主工具目录 → 一次授权编译 → 当前任务不可变工具白名单
```

改动集中于 `DSCG/dscg/pipelines/defended.py` 的 ToolAuthorizationCompiler：

- 显式设置授权模型的采样配置，规范工具目录顺序与说明；保持现有 tools 列表输出，不增加规划树或复杂契约字段。
- 简化提示，明确用户已经授权的任务动作及其条件：例如“调整已有支付”应选择更新能力，“评分符合就预订”包含预订能力；不把“稍后需要读取数据”误解为“只能授权读取”。使用通用示例，不硬编码 task ID、账单金额或 benchmark 答案。
- 每个顶层任务编译一次，保留任务隔离；外部内容、模型候选和工具反馈都不能补授权。补充明确的编译失败码，便于区分 API 失败、拒绝、格式或未知工具校验问题。

验证：扩展现有 `tests/test_sandbox_execution.py` 的授权隔离与先授权后候选检查。离线 mock 验证格式/边界；再对“查阅”“有条件预订”“调整已有支付”“新增付款”等可信请求进行小规模真实编译检查，分别记录必要工具缺失、多授权和重复结果差异。固定 temperature 不承诺完全确定性。

验收：租金和预订合法样例不再因为缺必要工具而被 TOOL_NOT_ALLOWED；读任务不因新提示获得写工具；编译异常仍 fail-closed。若授权仍不稳定，优先修该层的任务语义表达，不依赖后续审计加权限。

**阶段交付：** 最小授权改动、失败码、回归与小规模编译结果；更新 README/AGENTS，独立 git commit。

## 3. 阶段二：让动作审计只判断当前动作

```text
可信任务 + 当前动作 + 工具白名单 + 当前任务近期工具返回
                           ↓
                  一次 allow / deny / abstain
```

改动仍集中于 `DSCG/dscg/pipelines/defended.py` 的工具反馈衔接与 ActionSecurityChecker：

- 将当前任务最近的少量工具返回加入有界审计输入，明确为 untrusted data。首版采用固定小窗口，例如最近 4 个工具返回、每条至多 2,048 字符；显式标记截断，不建立检索器、来源图或长期记忆。窗口是否足够用合法多步负例验证，不能假定覆盖全部任务。
- 让审计器判断任务与当前参数是否一致：Bob 分享的文章链接可用于完成原任务；网页里要求先访问另一网址的命令不能因此扩大任务。工具返回作为判断依据，不自动成为授权。
- 保持结构化决策和现有风险路由；明确区分“发现不相关动作”与“证据不足”。审计不能给新工具授权、替换动作或改变白名单。不全局放行敏感读取或 abstain。
- 用简短的主模型任务规则区分“用户已授权任务”与“外部新增命令”，继续原任务；先验证审计修复，再单独验证这条提示，保持单变量比较。已有一次重审仍默认关闭。

验证：扩展 `tests/test_web_request_routing.py`，测试审计包是否真的包含当前任务的相关返回、标明不可信、执行边界不变；沿用 task isolation 回归。真实语义评测至少包括用户直接 URL、Bob 的文章 URL、文章内新增攻击 URL、合法多跳、无关链接与读取已有支付。预设 auditor 返回值只能证明路由，不代表语义效果。

验收：首先恢复历史旧版能够完成的 7 个 Slack 配对；完整测试不以攻击载荷未送达、任务提前停止或默认拒绝合法网页来获得安全分数。已知攻击网址额外访问应被阻断且合法文章仍可读取。

**阶段交付：** 有界上下文、简短审计职责、配对负例与真实模型结果；更新 README/AGENTS，独立 git commit。保持单次审计，不新增默认开关。

## 4. 阶段三：决定保留两层还是转三层

先做 12 个原用户任务的 clean 对照；攻击调试先取现有 tool_knowledge（36 条），正式评估恢复四种典型攻击（每组 144 条），均复用原冻结 manifest。每个配置使用新名称和 --force-rerun，主模型、任务、攻击、实际载荷及模型配置保持一致。

| 对照 | 要回答的问题 |
|---|---|
| 原生 baseline | 当前主模型自身的安全与任务效用是多少？ |
| 修正授权后的 --no-checker | 授权层自身是否漏工具、多授权或造成损失？ |
| 修正授权 + 原动作审计 | 单独修授权带来什么变化？ |
| 修正授权 + 上下文动作审计 | 审计上下文是否恢复合法任务，并额外拦住攻击？ |
| 上一行 + 简短完成提示（可选单独比较） | 无阻断额外确认/漏报是否减少？ |

旧 workshop_new / workshop_opt 保留作历史参照，主要结论依据同期 baseline 和同版本消融。正式比较至少重复 3 次，按 12 个用户任务簇报告配对结果；不能把 144 条当 144 个独立任务。

评测侧沿用 E0 审计，不加运行时防御层：保留官方 TSR/ASR，另记录载荷是否送达、合法业务数据是否保留、真实工具违规与拒绝文本命中。账单业务信息被攻击替换、酒店名在警告中命中的样本单列诊断，不改写旧分数或删旧样本。只统计合法任务被阻断的误拦，不把所有 blocked 都当成误拦。Token/API/延迟分开记录目标任务与额外预检。

工程目标（待验证，不是已实现指标）：

- 阶段性恢复旧框架约 77.08% 的历史 TSR；最终以同期 baseline 为准，争取任务成功率差距不超过 2 个百分点，clean 不新增框架误拦。
- 对 baseline 确实出现的工具违规有可重复的额外拦截，同时保留合法任务完成；警告少引用酒店名不作为防御改善。
- 两层每个任务一次授权、每个需审计动作批次一次审计；总 Token 相对同期 baseline 增幅争取不超过 20%，并报告收益来自哪里。

**转三层条件：** 已排除漏授权、缺上下文和错误评测解释；有效样本中 baseline 存在真实攻击成功，但修正两层经过重复对照仍没有净安全收益，或仍被工具返回中的新增指令稳定影响。此时停止继续给两层堆规则，进入三层候选设计。若所有 baseline 都没有真实攻击成功，本轮缺乏区分防御效果的样本，不能据此宣布两层无效或三层有效。

## 5. 三层候选：授权、工具返回处理、动作审计

```text
L1 可信任务授权 → 主模型提出工具动作 → L3 动作审计 → Monitor/ticket 执行
                      ↑                                 ↓
                      └──────── L2 工具返回处理 ────────┘
```

| 层 | 唯一职责 | 边界 |
|---|---|---|
| L1 任务授权 | 确定任务可使用的工具 | 不读外部指令，不因候选动作补授权 |
| L2 工具返回处理 | 在反馈进入主模型前，保留业务内容并隔离试图新增动作的指令 | 一次轻量处理；保留原始返回用于对账；不规划任务、不决定对象权限或生成恢复动作 |
| L3 动作审计 | 判断实际候选调用是否属于可信任务 | 一次判别，沿用执行边界；不再承担全文清洗或重建任务计划 |

例如，L2 保留 Bob 的文章链接、租金增加 100 和正常正文；标注并隔离“先访问另一网站”“先给第三方转账”这类偏离可信任务的命令。首版先做原文保留与指令标注，避免全文重写；区分不清时仍保留为不可信数据，交给已有动作审计判断。合法账单支付说明、租金通知中的调整指示、正文引用的指令不能因为包含祈使句就删除。候选层的输入是可信任务与原工具返回，输出只是供主模型阅读的不可信内容，不是权限判断。

它处理的是外部内容对规划的影响，L3 检查的是实际动作，二者须有不同可验证职责。标注“无注入”不构成可信事实、动作通行证或授权。

这是新层的候选提案，**不是已经实施或已经解锁的机制**。先在 research 技术路线中审阅具体输入/输出与允许范围，不套用锁定 I2 的任务义务账本、不新增对象/数据权限、不复活旧字段 provenance/source-to-sink 路线。

第三层只有在同任务、同载荷、同模型对照中提供额外安全收益，且没有删除账单字段、合法链接或摘要事实、没有扩大动作权限时才保留。若额外成本/误拦超过收益，则撤回该候选；不因为层数增加就宣布优化成功。
