# L2／L3效用优化方案：优先稳定L3，再验证正确写入

状态：**v3.4已实施，固定真实样本未通过效用验证**。用户后续授权跳过离线回归并直接调用Qwen；160次总请求内完成6条新策略和5条baseline计分，第6条baseline因预算未完成。方案原建议预算与三臂实验未整套执行，见[实施报告](./completed/v34_decision_contract_20261022.md)。cohort及历史结果不改。工程主线为AgentDojo banking／Slack；AgentDyn只做接口回归，其专项依赖授权问题另行处理。

## 1. 目标与选择

依据[最新256条配对分析](./completed/v33_tsr_analysis_20261022.md)，优先减少三类可定位损失：审计字段不合规、当前合法写入被来源污染连带否决、一次授权遗漏后续动作。协议失败与语义误拒分别测量，不能用一个TSR数字代替诊断。

| 路径 | 作用与代价 | 选择 |
| --- | --- | --- |
| 继续追加提示词 | 成本低，但当前已经有长度/当前动作规则，仍大量违反；不能约束字段 | 仅作语义澄清，不单独作为修复 |
| Schema约束＋精简协议＋清晰输入边界 | 不增加模型请求；同时改善格式和当前动作判断；需要版本化验证 | **推荐** |
| 更换审计模型、双重审计或失败后重问 | 成本/时延增加，难区分模型差异与框架收益 | 本轮不做 |

运行与安全边界：主模型/审计模型不换，思考、温度、重试数不变；不修补模型返回、不动态扩权、不绕过Monitor/一次性回执/票据。不改原生任务/攻击/评分，不按任务ID写策略，也不把协议失败从原生TSR分母中移除。

## 2. L3优先事项一：从有效JSON升级为受约束判决

### 2.1 两端使用同一份契约

当前L2/L3都发送`response_format=json_object`；该模式不保证字段结构。阿里云官方当前将Qwen3.7-Flash列入JSON Schema支持范围，提供`json_schema + strict=true`。因此先为当前DashScope北京业务空间做最小能力确认，再用共享Schema构建请求并在宿主重新校验。[官方结构化输出说明](https://help.aliyun.com/zh/model-studio/qwen-structured-output)

- 保留L3四字段：decision、violations、confidence、reason_code，禁止额外字段。
- decision固定为allow/deny/abstain；confidence保持有限[0,1]，不成为放行阈值。
- violations和reason_code使用有限短代码，不再让模型在代码字段写长段分析。reason_code初版集合：ALIGNED、OFF_TASK_ACTION、EXPLICIT_CONSTRAINT、UNSUPPORTED_PARAMETER、UNREQUESTED_DISCLOSURE、INSTRUCTION_AS_AUTHORITY、ORDER_VIOLATION、MISSING_EVIDENCE。
- violations只使用违规/缺证据代码，不含ALIGNED。宿主核对组合：allow必须无violations且reason=ALIGNED；deny须有具体违规代码（不能用ALIGNED/MISSING_EVIDENCE冒充违规）；abstain使用MISSING_EVIDENCE。无效组合仍失败关闭，不转换成allow或自动重问。
- Schema与宿主校验共用代码集合/长度/类型定义，防止再次出现“解析可过、记录不可过”。不降低Monitor校验标准；旧协议解析与历史回放保持原身份。现有有效读取deny例外保留并单列，模型判决和实际Monitor决定不能混记。

Schema只解决结构，不能保证判决正确。提供方拒答、截断、网络失败仍分别处理。官方不支持`uniqueItems`等关键字时不发送，重复名称拒绝、注册校验和跨字段语义仍由宿主做。

### 2.2 提供方适配与失败行为

- 首先只为官方声明支持且完成小样本验证的provider/model组合启用Schema；实际业务空间是否支持单独记录，不能仅用模型名字认证任意代理服务。
- DeepSeek等未确认支持的组合维持json_object请求与严格宿主校验，不假定全部OpenAI兼容接口均支持Schema。
- 格式在调用前确定；遇到Schema不支持时明确失败，不能在同任务内偷偷降级并发第二次请求。确需使用旧模式须使用独立、明确身份的运行。
- 主模型原生工具调用的生成方式不改；L2授权请求和L3审计请求使用此约束，不能把原生tool arguments JSON错误混进审计协议统计。

### 2.3 可定位诊断

默认仅新增安全字段：失败字段路径、预期/实际类型、数组项数、原始/规范化长度、结束原因、有效格式与Schema身份。分别统计JSON语法、字段集合、字段类型、短代码、decision一致性、API/超时、Monitor记录与回执错误。

默认日志不输出原始参数、响应或凭证。固定诊断如需查看实际审计输入，沿用现有full附件，在受控新目录保存；保存事实不代表认证其真实性。不得把重构历史输入冒充当时真实请求或复用旧请求哈希。

## 3. L3优先事项二：只判断当前一步的用途和参数依据

### 3.1 输入边界

继续使用可信用户请求、当前动作、原生schema/effect和有界工具证据。优化组织与来源标记，不先增加预算或模型摘要：

1. 可信请求保留原文；工具返回不能被改写为新的用户指令。现有有限委托继续沿用原边界。
2. 每个当前动作单独列出实际效果、完整原生参数和执行目标；一批多调用仍采用整批审批，任一不通过则整批不执行。
3. 工具证据保留调用名称/参数、返回内容、错误和来源ID；区分成功返回与DSCG_BLOCKED、工具异常，不能把错误文本当业务事实。
4. 对目标、金额、正文选择相关证据，记录实际选入/省略/截断情况；仅有证据链接不等于参数已被事实支持。默认预算先不变。
5. 可以展示“参数值在用户原文中出现”“与某来源文本匹配”的本地观察；它不是授权、因果溯源或真实性认证，也不能覆盖否定语义。

L2步骤可以保留在日志，但不作为L3放行证明，不构建任务义务ledger或模型自述的完成oracle。只有发现实际证据缺失时，才对现有选择器做最小调整并单独比较。

### 3.2 判决原则

| 当前情况 | 预期判断 |
| --- | --- |
| 用户明确指定的地址/收件人，当前操作服务于其中一个子任务 | 可以完成当前一步；不要求同次调用完成全部子任务，也不虚构身份验证门槛 |
| 用户要求从指定来源取得地址/邮箱/文章等事实 | 可把相关事实用于既定任务；事实来源不是新增任务的授权来源 |
| 需要先读才能计算退款/选择频道 | 读取阶段不要求提前知道后续金额/目标；写入时检查已有事实与推导关系 |
| 来源同时含正常内容与注入文本，当前正文/目标未执行注入 | 不能仅凭“发现注入”拒绝当前合法动作 |
| 当前动作转向攻击收款人、无关外发或转发非用户要求的攻击命令 | deny并给出具体参数/用途违规代码 |
| 当前必要证据实际缺失 | abstain；明确缺什么，不因泛化可疑性拒绝 |

短提示保留在约1200英文字符内，JSON字段规范移入Schema。重点澄清任务分步、事实使用和外发正文，不累计旧候选长提示。正例与相邻负例必须成对验证；用户明确要求引用/分析恶意文本的场景也单列，不能机械禁止引用。

### 3.3 读取路由单独验证

首轮保持read-purpose-v2范围：public/internal合格读取，personal/secret及效果性调用仍审计；不通过改风险标签扩大免审。CLI shadow仍实际审计，selective才实际应用候选。

先把读取上的字段失败与写入误拒修清，再做同候选shadow/selective对照。banking目前没有普通候选，不能承诺切selective会改善它。若后续考虑部分personal读取成为候选，作为独立设计/实验，不能与本轮协议和写入变化混在一起；secret、外部副作用和AgentDyn handler不能因名称像读取而获豁免。

## 4. L2：保留完整定义，减少重复输出，聚焦用户要求的动作

### 4.1 新协议建议：只生成动作授权步骤

保留完整原生名称、描述、参数schema和自动读取标记。模型不再重复枚举已自动可用的读取；输出仅描述可信请求中的效果性子目标和候选动作工具：

```json
{"steps":[{"intent":"按通知调整已有租金付款","tools":["update_scheduled_transaction"]}]}
```

- 各tools使用本次注册的待选择动作工具枚举；steps/intent/数组长度均有界。
- 宿主严格验证，再由步骤工具并集产生动作授权，合并原自动读取规则；不再要求模型另写一份顶层tools与并集完全一致。
- 这只消除重复表示和减少格式负担，不把缺失动作自动补入，也不将错误步骤视为合法。纯读取可返回空steps；无法从语义上证明其完整性。
- 显式旧候选、受限host profile与冻结诊断保留原协议；新协议单独绑定身份。

### 4.2 授权语义

以用户要求的结果组织步骤：退款、调整付款、发摘要、邀请并加群等，避免只列“先读取”而丢后续动作。未知金额/邮箱/频道不阻止选择已被用户要求的动作工具；相关候选有歧义时可同时保留，但无关写入、明示禁令、纯读取请求不能因此获写权限。宿主权限上限与注册检查保持。

“按文件办事”且未明示动作的情况不能靠静态猜测解决。仅使用现有受支持的有限委托；不把任意读到的内容或包含注入的文件升级为授权，不因为工具报缺权限就动态补权。此类任务的剩余损失明确报告，不承诺通过更宽名单全部修复。

L2 error、合法空动作授权、合法列表遗漏分开记录。授权失败后工具视图的失败状态应明确可诊断；不让主模型凭空编造工具，也不将此类原生utility=false删除出分母。

## 5. 规划侧只做必要联动

- 说明：可用工具能查询的正常事实应先查询；无需因为正文存在注入而放弃与之无关的合法步骤。
- 保留来源中的真实对象标识，不能擅自截断/编码频道名；把标识里的指令当数据不等于执行指令。
- 工具被阻断或无返回时，不应声称已完成；允许明确报告部分完成。新增记录只能核对实际工具返回，不能假装证明完整任务成功。
- 不新增完成催促、自动重试、自动补动作或输出修复。先诊断再作小幅提示澄清，单独验证，不与L3收益混记。
- 排名模板、欠指定任务要求不改环境等原生评分敏感项保持原样；不能为追TSR按任务ID硬编码答案。

## 6. 分阶段验证与成本控制

### A. 离线契约与真实套件模拟

覆盖两个后端的Schema请求、提供方适配、L2新协议、L3四字段/决策一致性、来源事实与恶意命令相邻正反例、未完成后续步骤、整批拒绝、Monitor/一次性票据、旧回放与缓存身份。验证无额外请求/重试，未知provider无偷偷降级。

真实native套件配合模拟响应验证流程，不能称为模型授权质量或ASR/TSR已改善。继续运行双环境Python、Node、两入口help、文档链接与diff检查。

### B. 可另行授权的有限真实组件验证

建议第一轮控制为**98次请求上限**：

- 2次Schema能力确认（L2、L3各1），失败就停止，不补发旧格式。它仅验证接口接受请求和返回可校验，不证明服务端对全部Schema语义的保证。
- L3：6正例＋6个只改一个关键因素的负例 × 当前/仅Schema/Schema＋语义三组 × 2次重复＝72次。
- L2：3个复杂授权正例＋3个读取/禁止/无关写入负例 × 当前/新方案 × 2次重复＝24次。

L3正例固定来自banking退款、文件地址、首次搬家地址；Slack频道摘要、邀请加群、网站反馈。负例分别换攻击收款人/目标/正文等；使用真实注册工具、有效sandbox和已确认来源上下文，不能重复此前缺授权的诊断错误。L2覆盖房租、退款、复合请求及读写边界。

固定输入仅为机制诊断，负例为人工审核的预期，不冒充原生ASR或生产安全真值。记录每次开始/结束、成功API的Token和实际请求配置；首个API故障或预算耗尽停止，不自动补次数。此预算仅为建议，未开始调用，也不复用此前已耗尽预算。

### C. 固定原生小样本与扩大条件

1. 先固定banking user_task_3/13/15、Slack user_task_3/11/16共6个用户，baseline/当前v3.3/新候选三臂clean，共18条轨迹。使用独立请求/Token上限；轨迹数不是请求数。
2. 再用相同6用户、各场景从原冻结cohort按注册顺序取一个目标、一个已注册攻击做三臂小攻击对照，保持原生GOAL预检；不得按既有ASR选容易目标。此阶段仍为诊断，不能作为正式ASR。
3. 小样本用partial的现有自定义task manifest，明确标记诊断范围。默认partial仍是原前三用户×前三目标；`--task-manifest`和`--cohort`互斥，不能一起传。正式cohort测量保留全部用户及原冻结目标。
4. 达标后才考虑banking＋Slack完整37用户clean，再到同cohort匹配攻击；不自动扩跑全97个clean或所有场景。给每阶段重新限定预算。

为了区分因素，组件比较包含仅Schema；原生小样本比较同时列L2错误、L3协议/有效判决、规划无调用与实际执行，不能从组合候选成绩反推各组件独立收益。shadow/selective对照保持同一候选、数据和模型设置，仅改变模式。

## 7. 验收、停止与推广

| 检查 | 进入下一阶段的条件 |
| --- | --- |
| 离线协议/执行 | 所有约束、失败关闭、回执/票据、旧记录和任务分母回归通过 |
| 小组件格式 | 固定诊断上L2/L3字段失败为0；这只是有限样本门槛，不宣称生产错误率为0 |
| 小组件语义 | 六个合法L3场景能正确通过，配对负例无新增allow；L2正例不再漏预定动作，负例不增无关写权限 |
| 原生clean | 目标失败链路出现实质恢复，既有正常项不新增退步；否则逐案例回查，不靠删除样本达标 |
| 小攻击 | 记录实际投递、原生utility/security、错误和缺失；出现新增不安全动作则停在当前阶段，不自动推广 |
| 完整对照 | 任务/配置可比，TSR、ASR、联合成功、有效/错误分母、Token与墙钟完整；只有通过后才考虑默认推广 |

不能以ASR=0、shadow无分歧、少量负例通过或统计不显著证明非劣/安全。约5个百分点clean差距若继续保留，只作为未来目标，不作为本轮可保证成绩。TSR失败不因L2/L3协议错误被排除，既有基础设施null样本继续沿用原规则。

## 8. 实施位置与兼容

| 位置 | 最小改动职责 |
| --- | --- |
| 新的共享判决Schema模块 | 有限代码、Schema、提供方请求格式；不建立通用工作流引擎 |
| dscg/pipelines/defended.py | L2/L3请求、严格解析、当前动作输入与安全诊断 |
| dscg/authorization_steps.py | 只含动作步骤的新输出协议及并集派生 |
| dscg/audit_context.py | 有证据时才调整来源选择/呈现，不先泛化事实认证 |
| 共享factory/runner和两个CLI | 同时应用有效策略并记录身份，保留原任务/目录/并发/progress行为 |
| tests与指南 | 原生模拟、公共协议、兼容和阶段对照说明 |

新协议、提示、有效请求格式与Schema摘要进入已有防御/缓存/回执绑定；不增加源码扫描，不放宽旧测量身份。实施时使用新的防御身份和运行name，具体名称实施时统一确定；不重命名旧DSCG_v3.3或重写旧manifest。

冻结cohort仍按当前模型ID/provider、后端/版本/场景轻量读取，不能因防御Schema改变要求重新预检。baseline仍用原生流程。所有变化须在run_benchmark、run_partial_benchmark和cohort共用路径验证；不另做仅诊断脚本有效、正式入口无效的策略。

推荐实施顺序：**L3协议与诊断 → L3语义/证据边界 → L2协议与授权覆盖 → 必要规划澄清 → 阶段对照**。各阶段可单独撤回，不能一次混改后只看总TSR。
